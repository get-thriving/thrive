# ADR 0018: Image store

## Status

Accepted (2026-10-29). The store, the model, the use cases around the picture of
a user, and the account page where people change it are implemented. Still to
come, and marked _planned_ below: pictures from a social login, and the job that
reconciles the store with the database.

## Context

Users should have a profile picture: one generated from their name, one that
comes with a social login, or one they upload. That needs somewhere to keep
images. The domain database is the wrong place: the avatar used to be a base64
SVG in the user row, which every load of a user drags along, and uploads are
bigger.

Hosted Thrive runs on Render, whose services have no shared disk, while a
self-hosted install is a compose file with one volume. Pictures of other
kinds (images inside docs, say) will want a place of their own later. And a
removed picture has to really be gone.

## Decision

### A port, chosen by the backend blend

`ImageStore` (`jupiter.core.images.store`) is a port like search is, built once
per process and handed over in `JupiterPorts.image_store`. It deals in bytes
and knows nothing about users:

| Method                            | What it does                                                 |
| --------------------------------- | ------------------------------------------------------------ |
| `put(purpose, path, image)`       | Save, replacing what is at the path                          |
| `load(purpose, path)`             | The image, or `ImageNotFoundError`                           |
| `remove(purpose, path)`           | Idempotent: removing what is not there is fine               |
| `list_images(purpose)`            | Every image of this instance and purpose, with size and time |
| `get_serving_link(purpose, path)` | An `ImageLink`: a URL, and when it expires if it does        |

A _purpose_ (`ImagePurpose`, only `avatars` for now) is its own bucket or
directory, so a new use of images gets a clean namespace and its own rules.
A _path_ (`ImagePath`) is a relative path of lowercase segments ending in a
known image extension. It lands in file names and URLs, so the value rejects
anything else (`..`, hidden files, uppercase, unknown extensions) instead of
trusting the layers below. New paths are `<192 random bits as hex>.webp`.

A store belongs to one instance. Instances of an environment share a bucket
(the staging ones, one per PR, are created and dropped without any
infrastructure change), so every image sits under the instance's namespace, and
`list_images` never shows another instance's. Names that come from branch
names are flattened to `[A-Za-z0-9._-]`.

Two implementations, picked by `WEBAPI_IMAGE_STORE`, a new entry in the ADR
0008 table:

| Value   | Where images go                                                | Links                                |
| ------- | -------------------------------------------------------------- | ------------------------------------ |
| `local` | `<IMAGE_STORE_LOCAL_ROOT>/<purpose>/<instance>/<path>` on disk | Relative: `/images/<purpose>/<path>` |
| `gcs`   | A Google Cloud Storage bucket per purpose, under `<instance>/` | The public URL of the object         |

Settings other than the blend token stay in service config, as ADR 0008 says:
`IMAGE_STORE_LOCAL_ROOT` (default `images`), and for `gcs`
`IMAGE_STORE_GCS_CREDENTIALS` (a service account key as JSON, a secret) and, per
purpose, `IMAGE_STORE_GCS_<PURPOSE>_BUCKET` and an optional
`IMAGE_STORE_GCS_<PURPOSE>_PUBLIC_BASE_URL`. Only the chosen store's settings
are checked, and a missing one stops the process at startup. They are read by
`ImageStoreProperties.from_env`, held by every WebAPI process, and built into a
store by `build_image_store`. The CLI is local-only like its database, so it
always uses `local`.

By universe: **Thrive** (Render) uses `gcs`, everything else `local`. On a
self-hosted install the images sit in `/data/images`, on the volume that holds
the SQLite database, so one backup has both.

### Serving: straight from the bucket

Hosted avatars are served from the public bucket, with no hop through our
servers. They are not secret (the product already treats unlisted links as
capabilities, ADR 0010), they never change at a given URL, and they are tiny.
So each image gets a path nobody can guess, is uploaded with
`Cache-Control: public, max-age=31536000, immutable`, and a replacement is a new
path. Anyone can fetch an object they know the name of, but nobody can list the
bucket.

Signed URLs were rejected for this: they are not one-shot (a V4 URL works for
whoever holds it until it expires), but they differ on every load, which defeats
browser caching, and every avatar in an API response would need signing.
Proxying everything through the WebUI costs a hop per image for nothing. Both
fit content that does need a per-viewer check, such as private attachments, and
`get_serving_link` is async and returns an expiry so such a store can slot in.

The database keeps the path and never the URL, and links are computed. Putting a
CDN or a custom domain such as `images.get-thriving.com` in front later (a load
balancer with a backend bucket and Cloud CDN, since a CNAME to Google does not
do HTTPS) is only `IMAGE_STORE_GCS_AVATARS_PUBLIC_BASE_URL`. Worth doing once
there is a strict CSP to feed one origin to, or avatar URLs end up where they
can't be rewritten (emails, exports).

A browser can't read the `local` store's disk, and the WebUI does not mount the
WebAPI's volume. So the WebUI serves `/images/<purpose>/<path>` itself, as a
resource route (`serveImage` in core, behind `routes/images.tsx`):
unauthenticated like the public bucket (the path is the secret), it calls the
guest `ImageLoad` use case, decodes the base64 in the result, and answers with
the same immutable cache header and `nosniff`. A path that is wrong in any way is
the same 404, so that probing tells nothing. The link is relative so it resolves
against whichever server the app talks to (ADR 0015), with no host or port to
configure. Upload takes the same base64-in-JSON shape, since the use case
framework has no binary transport.

An `ImageUrl` is also what the generated picture of a user is: an inline
`data:image/svg+xml;base64,` link, as it has always been. No other kind of data
URL is accepted.

### Infrastructure

Terraform declares `thrive-production-avatars` and `thrive-staging-avatars`:
uniform bucket-level access, `allUsers` as `objectViewer`, no object versioning
and soft delete turned off (a removed picture is gone, not kept for a week), and
a 7 day expiry on staging. One service account, `image-store`, is
`objectAdmin` on both. Render hands previews the same secrets as production (as
with the Algolia key, whose index name is what tells the environments apart), so
a per-environment account could not be wired, and the bucket name in config is
what separates them. Its key is a sensitive terraform output, pasted into the
`jupiter-webapi-secrets` group on Render by hand.

### Normalising

Every incoming image goes through `ImageNormaliser` before it reaches the store,
so the store only ever holds square WebP pictures of one bounded size with
nothing else in them:

- At most 4 MB, and at most 40 million pixels, which is read off the header
  before anything is decoded.
- JPEG, PNG or WebP only. SVG can carry scripts, and HEIC needs a native decoder
  we decided not to ship.
- Rotated the way the camera meant it, then stripped of all metadata, since
  phones record where a photo was taken. Colours are moved to sRGB first, so a
  wide-gamut photo does not go dull once its profile is dropped.
- At least 128 px on the short side, judged after the rotation. Cropped square
  around the middle and scaled down to at most 256×256, never up.
- Animated pictures keep their first frame. Transparency is kept.

### Choosing a picture

The Account page has a Picture section: the current picture, an upload button,
and a button to remove it that shows only once there is one to remove. A file
picked there goes to the page's own action as a multipart `upload-avatar`, which
base64s it for `UserAvatarUpload`. It goes through a fetcher of its own, not the
form of the section, since a form that posts a file cannot also scale it down
first. The action takes the file from the request itself and leaves it out of
the form schema: `parseForm` (zodix) turns every non-string entry into JSON, and
a file does not survive that. The button stays disabled until the page has
hydrated, since a picture chosen before then would go nowhere.

Phone cameras make photos bigger than the 4 MB the WebAPI takes, so the browser
scales anything over 3 MB down before sending: the long side to 1600 px, as a
JPEG, or as a PNG if it was one, in case it is see-through. The WebAPI then
crops and shrinks it as it does any picture, so the scaling only has to get it
under the limit. If the browser cannot read the file (most cannot read HEIC), it
is sent as it is, and the WebAPI says what is wrong with it. A file still over
4 MB is refused in the browser, with the same words, before anything is sent: a
proxy would only answer a request that big with an error page.

The self-hosted nginx allows request bodies of 8 MB (its default is 1 MB), which
is room for the largest picture and the form around it.

### The model

- `Image` is a `LeafSupportEntity` under `User`, like `OAuthGrant`: no sharing
  rules, and skipped by the search indexer. It holds the purpose, the store
  path, content type, size, dimensions, a hash of the bytes, and where the
  picture came from (`uploaded`, later `google`).
- `User` drops its stored `avatar` and points at its picture with a nullable
  `avatar_image_ref_id`. `None` means the picture generated from the name, drawn
  when needed and stored nowhere. Every avatar so far was generated, so the
  migration loses nothing. The pointer has no foreign key: the image sits under
  the user, and Postgres has to be able to delete them in any order.
- `LoadTopLevelInfo` and `UserLoad` return `user_avatar_url`, the link to show:
  the store's link for the picture the user chose, or the generated one. A
  pointer to an image that is gone falls back to the generated picture rather
  than failing a page.
- `UserAvatarUpload` normalises the picture, stores it, and only then points the
  user at it, so the database never names an object that is not there. If the
  database refuses it, the new object is removed. The picture it replaces has
  its row hard-deleted in the same transaction, and its object removed after
  the commit. `UserAvatarClear` does the same without a new picture. A picture
  is never edited: a new one is a new path.
- A refresh from a social login may only replace a picture that login brought
  itself, never one the user uploaded (`ImageSource`). _Planned._

### Cleanup

Orphans come from a crash between storing an object and committing its row, a
failed delete after the commit, and above all removing a user, since
`generic_destroyer` cascades through rows and knows nothing of buckets.

- The abandoned-users cron removes a user's objects **before** destroying them.
  If the store fails, the user stays and is tried again tomorrow, so a row
  always outlives its object and nothing is left that nobody can find.
- Closing an account only archives it, so the rows stay; the objects, which are
  publicly fetchable, do not. They are removed once the account is archived,
  and a failure there is logged and does not stop the account closing.
- The dev-only `remove_all` and `nuke_all` helpers remove them too, so the test
  stores stay tidy.
- _Planned._ A daily reconciliation job lists the instance's objects and rows,
  and removes what lacks its counterpart once it is a day old. It refuses to
  delete if the database holds no images while the store holds many, and caps
  deletions per run.

## Consequences

- Images do not move between `local` and `gcs` by themselves. Switching the
  store of an existing install means copying the objects over.
- `local` keeps images on one disk, so it does not suit several WebAPI replicas
  unless they share the volume.
- A public image stays fetchable at its URL, and in caches, until deleted or its
  year-long cache expires. For avatars that is accepted.
- The service account key lives in terraform state, and a preview environment
  can read production's credentials, as it can the other shared secrets.
- Two staging instances whose names differ only in characters flattened to `-`
  would share a namespace. Their paths are random, so nothing is exposed.
- Every WebAPI process, the cron workers included, builds an `ImageStore`, and
  core gains dependencies on `google-cloud-storage` and Pillow.
- The OpenAPI spec lists every value and enum in core, so adding one means
  regenerating `gen/`, whether or not a use case uses it.
- Closing an account removes the picture for good, whatever later becomes of the
  archived rows.
- The dev tooling passes the blend through the environment only. There is no
  `--webapi-image-store` flag for `mise run run:srv`, and development uses
  `local` with a directory next to each instance's database.
