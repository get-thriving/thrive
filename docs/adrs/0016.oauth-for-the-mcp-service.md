# OAuth for the MCP service

## Context

[ADR 0004](0004.api-and-mcp.md) gave the MCP service one way in: an MCP key,
owned by a user, carried in the URL (`/v1/{mcp_key}/mcp`) and swapped for a
short-lived token. That fits a script or a local process. It does not fit a
remote client like Claude Code, which expects the MCP authorization spec
(OAuth 2.1): a `401` pointing at protected-resource metadata, a browser sign-in,
and a bearer token that is refreshed. A secret in a URL is also easy to leak.

## Decision

The MCP service is the OAuth resource server and also fronts the authorization
server. Access tokens are the `stamp_for_mcp` token that the key exchange already
produces, so nothing downstream of the service changes.

* **Discovery.** `GET /.well-known/oauth-protected-resource` and
  `GET /.well-known/oauth-authorization-server`. PKCE `S256` only, public
  clients (`none`), and `client_id_metadata_document_supported`. Dynamic client
  registration is left out for now.
* **Challenge.** `/mcp` without a live bearer token answers `401` with
  `WWW-Authenticate: Bearer resource_metadata="…"`. The service reads only the
  expiry of the token, to ask clients to refresh early. The signature is checked
  by the web API on every call, as before.
* **Sign-in.** `GET /authorize` validates the request and redirects to the web UI
  (`/app/oauth/authorize`), which reuses the normal login (password login returns
  to the request through a path-checked `returnTo`) and asks the user to consent.
* **Grants live in core.** An `OAuthGrant` entity sits under the user, next to the
  MCP key. It holds the consent (client, redirect URI, resource, PKCE challenge),
  a one-time code (10 minutes), and a rotating refresh token (30 days). Secrets
  are stored hashed. Use cases: `OAuthGrantCreate` (logged in, from the consent
  page), `OAuthTokenExchange` and `OAuthTokenRefresh` (guest, from `POST /token`).
* **Redirect URIs** must be a loopback address (`localhost`, `127.0.0.1`, `[::1]`,
  any port) or one of a short allow list of hosted clients. The check lives in
  core so it is made once, before any redirect.
* **Issuer identification (RFC 9207).** The metadata sets
  `authorization_response_iss_parameter_supported`, and the redirect back to the
  client carries `iss`, the issuer. `/authorize` hands the issuer to the consent
  page as `issuer`, always its own value whatever the request said, and the
  consent page repeats it as `iss`. ChatGPT uses its stable redirect URI, which is
  on the allow list, only with a server that does this. Otherwise it uses a
  redirect URI per connector, which cannot be listed in advance. This is expected
  to be enough, but it has not been tried against ChatGPT itself.
* **Replay.** Redeeming a code twice, or presenting a refresh token that was
  already replaced, archives the whole grant. Archiving is also how a grant is
  revoked.
* The MCP key and `/v1/{mcp_key}/mcp` stay, for scripts and stdio.

## Consequences

* New configuration for the MCP service: `PUBLIC_URL` (its external base URL) and
  `WEBUI_URL`. They are set for dev and CI (pm2), Render and the self-hosted
  compose file.
* The way back to the consent page travels as a `returnTo` in the url, through
  password login and through the Google and Apple redirect flows: `prepare` adds
  it to the callback urls, the `ready` pages keep the query, and
  `create-or-login-user` sends a verified user back to it. It is checked at every
  step to be a consent page path. The native sign in of the mobile apps does not
  carry it, since a connect never starts there.
* The self-hosted nginx (`infra/self-hosted/webui.conf`) forwards `/authorize`,
  `/token` and the two `/.well-known/oauth-*` documents to the MCP service as exact
  matches at the root of the domain, since that is where clients look up the
  authorization server metadata. They are not tied to `/mcp`, so other clients can
  use them later. It also rewrites an MCP key url, `/mcp/v1/<key>/mcp`, to the
  `/v1/<key>/mcp` that the service serves. Hosted deployments serve everything from
  the MCP origin directly. `itests/connections/mcp.test.py` checks all of this
  through whatever fronts the service.
* The Access page lists connected apps and lets the user revoke them.
