# ADR 0013: Client-reconciled mutations in the time plan view

## Status

Accepted (2026-09-14)

## Context

The time plan view (`routes/app/workspace/apps/time-plans/$id.tsx`, with the
activity panel `$id/$activityId.tsx` and the leaves under `$id/`) is one of the
heaviest pages in the WebUI. Its loader pulls the plan, every activity and its
target, doneness, the journal and the calendar. Every edit used to go through a
route action that redirected, and the redirect made Remix run every loader on
the page again — about three seconds for each status change, kanban drag or
field save.

Two things made this hard to fix within the usual Remix flow:

- Remix v2 (classic compiler, no single fetch) has no per-submission opt-out of
  revalidation. `shouldRevalidate` can only look at the submission after the
  fact, and fetchers still revalidate on completion.
- The page renders the same entities in several places (activity list, kanban,
  calendar, the panel), so patching one loader's data by hand drifted out of
  sync quickly.

## Decision

Edits in the time plan view are applied locally, posted to resource routes with
`fetch`, and reconciled with what the server returns. Nothing is revalidated
for them.

### The store *(`apps/time_plans/store/`)*

- `store.ts` keeps entity tables keyed by `ref_id` (activities, inbox tasks, big
  plans and their stats, todo tasks, habits, chores, their stacks, time event
  blocks).
- Tables are fed by **sources**: one snapshot per loader (`plan`, `activity`,
  `calendar`; see `snapshots.ts` and `calendar.ts`). A reloaded source replaces
  what it contributed; entities other sources still hold stay.
- **Pending mutations** are applied over the confirmed state
  (`selectTimePlanEntities`). They survive reseeding, so a reload that lands
  mid-save doesn't undo an edit that hasn't been confirmed yet.
- When a mutation resolves, its **delta** is merged with a version check (a
  stale copy never replaces a newer one), and `removed` keys are dropped.
- `context.tsx` provides the store from `$id.tsx`, syncing sources during render
  so the store is filled on the server too.
- Routes render from the store: `view.ts` (`selectTimePlanView`,
  `latestEntity*`) mirrors `TimePlanLoadService`'s rules, and doneness is
  derived client-side with a TS port of the Python rules, tested against the
  same cases.

### Mutations *(`store/mutation.ts`, `store/mutations/`)*

A mutation is a descriptor:

```ts
interface TimePlanMutation<Args, Result> {
  action: string; // the resource route
  toFormFields: (args: Args) => Record<string, string>;
  applyOptimistic: (entities, args) => entities;
  toDelta: (result: Result) => TimePlanEntityDelta;
  source?: string;
}
```

`useTimePlanMutation` enqueues the optimistic change, posts the fields, and
resolves or rejects the pending mutation. Failures show a snackbar, because the
panel that started the edit is often closed by then. Business rules the server
would otherwise apply (inbox task status and delay dates, big plan status,
kanban moves) are pure functions next to their apps, with tests.

### Resource routes *(`time-plans/mutations/*`)*

Each route calls one use case and returns
`json(noErrorSomeData({...entities}))`. For this to work, **update, create,
archive and remove use cases return the entities they changed** (`updated_*`,
`new_*`, `archived_*`, `removed_*_ref_ids`), including related entities saved in
the same transaction (e.g. an inbox task's big plan stats).

### Forms keep working unchanged

Editors still render `SectionCard` forms posting an `intent`.
`IntentInterceptorProvider` / `LeafPanel.intentHandlers` catch the submit and
hand the form data to a handler that runs the mutation, so editors shared with
the rest of the app don't need to know about the store.

### Panel loads

The activity panel loads through `TimePlanActivityLoadForPanelUseCase` (WebUI
only): one call returning just what the plan doesn't already have. Summaries and
tags come from the plan's own loader.

### What still reloads

Anything that can change entities the client can't predict keeps full
revalidation: changing the plan's time config, archiving/removing/publishing the
plan, habit/chore regen (offered after edits that change generation), and the
`add-from-*` association flows. Coming back to the tab after five minutes also
reloads the view, unless edits are still pending
(`store/revalidate-on-return.ts`).

## Consequences

- Most edits in the time plan view take one small request and no reload.
- **Returning entities is part of the use case contract.** New update-like use
  cases should return what they changed, or the client can't reconcile.
- The client has to model some server rules. Keep them as pure, tested
  functions; where a rule already exists in Python (doneness), mirror its test
  cases.
- Views can drift from the server when something else changes the same
  entities (gen, other devices, collaborators). The return-to-tab reload and the
  explicit regen are the answer for now.
- There is more code than a plain action + redirect: a descriptor, a resource
  route, and a handler per intent.

### When another view should opt in

Worth it when a page's loader is expensive **and** its edits are frequent, local
and predictable (status changes, drags, field saves). Not worth it for pages
that are cheap to reload or whose edits have wide, hard-to-predict effects —
stay with actions and revalidation there.

The framework migration (Vite → single fetch → React Router v7) replaces the
internals of `useTimePlanMutation` with the per-submission revalidation opt-out
and `useOptimistic`. The descriptors, routes and store can stay.

## Update (2026-09-25)

That migration has landed, so the Context above is a record of how things stood
under Remix v2, not of how they are now:

- The WebUI and Published run on React Router v7 with single fetch enabled, so
  the per-submission revalidation opt-out this ADR works around now exists.
- The route modules moved into core with the rest of their app: the time plan
  view is `core/apps/time_plans/routes/time-plans/$id.tsx`, and the resource
  routes are under `time-plans/mutations/` there.

The decision itself stands unchanged - edits are still applied locally, posted
to resource routes and reconciled - and swapping the internals of
`useTimePlanMutation` is still open.
