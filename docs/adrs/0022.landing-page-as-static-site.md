# ADR 0022: The landing page is a static site

## Status

Accepted (2026-11-22)

## Context

get-thriving.com was a Wix site. We want the landing page in this repository,
looking like the product (Strata, [ADR 0019](0019.ui-styles.md)) and built with
the tools we already use. The first question was which technology.

What the page needs:

- Pages that never change between visits: a home page and the two legal pages
  (`/terms-conditions` and `/privacy-policy`, which `Config.global` and the apps
  link to).
- One piece of client-side state: the tabs over the sample screens.
- No data from the WebAPI, and no forms. The old site's newsletter form was
  dropped, so nothing on the page needs a server.
- Links to the apps, the docs, the community and the source.

## Decision

- **A new service, `src/landing`, built with React Router in framework mode with
  `ssr: false` and `prerender`**, the same toolchain as `webui` and `published`.
  Every page is rendered to a file at build time and hosted as a **Render static
  site**, the way `jupiter-docs` is. There is no Node process and no Docker
  image.
- **Every page is listed in `prerender`** in `react-router.config.ts` as well as
  in `routes.ts`. A route missing from the first has no page at all.
- **No MUI.** The page is markup and one stylesheet. Colors are the Strata CSS
  variables (`strata-tokens.ts`, `StrataColorVariables`), imported from core, so
  there is one palette and no hex values in the page. Fonts are self-hosted
  (`@fontsource/ibm-plex-*`).
- **The page follows the device's color scheme**, as the published pages do. A
  script in `<head>` sets `data-color-scheme` before the first paint. Unlike the
  app's script it sets no cookie: with no server nothing would read it.
- **Links are fixed when the page is built.** `vite.config.mts` reads
  `WEBUI_URL`, `DOCS_URL`, `COMMUNITY_URL`, `SOURCE_URL` and `SUPPORT_EMAIL` from the
  environment and then from `src/Config.global`, and stops the build if one is
  missing, so a local build points at the local WebUI and nothing is silently
  defaulted.
- **On Render, production links to the hosted domains.** `RENDER_EXTERNAL_URL`
  is the `onrender.com` address even for a service with a custom domain, so
  `tasks/build/landing.sh` links production to the `HOSTED_GLOBAL_*` URLs. Only a
  pull request preview (`IS_PULL_REQUEST=true`) takes `PREVIEW_WEBUI_URL` and
  `PREVIEW_DOCS_URL` from `render.yaml`, so it links to its own services.
- **Part of `run:srv`, in the pm2 mode only.** Like the docs, the page runs
  beside the other services of an instance, and `run:srv` hands it that
  instance's `WEBUI_URL` and `DOCS_URL`, so its links point at the instance. It
  needs no instance to run, so `mise run run:landing` still starts it alone, and
  `mise run build:landing` builds it. Callers of `run_jupiter_webapp` that don't
  pass a landing port (CI, itests, client-code generation) don't get one.
- **Not part of the self-hosted compose.** A self-hosted install serves the
  WebUI at its root; the landing page is for the hosted domain.

### Alternatives considered

- **React Router with a server, like `published`.** The same stack, but a Node
  container for pages that never change, and `published`'s weight (MUI and
  emotion server rendering, editor and chart dependencies) to carry or cut.
  Worth it only if the page needed to post to our own server.
- **Astro.** The best fit for a content site, but a third framework to learn
  and keep up, with the tokens to re-export as CSS.
- **Plain HTML and CSS.** The lightest, but it shares nothing with the Strata
  tokens or with how the other services are built.

## Consequences

- The landing page costs a static site's hosting and has nothing to patch or
  keep running.
- Adding a page means a route, a `prerender` entry and, if it is linked from
  outside, keeping its path stable: the apps link to the legal pages.
- Anything that later needs a server (a form, a changelog read from the WebAPI)
  has to go through an endpoint of the WebAPI or the API, called from the
  browser, or this decision has to be revisited.
- The page is dark and light for free, but only the dark scheme was designed; a
  change to the design should be looked at in both.
- Moving get-thriving.com from Wix is a DNS change made outside this repository,
  after the site has been checked at its own address. The legal pages must be
  live at the same paths before it.
