# ADR 0014: Section filters live in the URL

## Status

Accepted (2026-09-29)

## Context

Almost every page in the WebUI (and a few in Published) shows a
`SectionActions` bar with filters: a view or grouping picked from a few options
(`FilterFewOptions*`), or tags, contacts, aspects and the like picked from many
(`FilterManyOptions`). Those choices were kept in component state, so they were
lost on a reload, could not be linked to, and were reset whenever a panel was
opened on top of a page and closed again. The time plan view had grown its own
ad-hoc `timePlanView` / `timePlanGrouping` query params to work around this for
two of its filters only.

Pages load everything they show and filter on the client, so a change of filter
never needs new data. React Router, however, reloads every route on screen
whenever the query string changes.

## Decision

- Every panel with filters has a **panel id**, and every filter in it a
  **filter name**, both kebab-case. A filter's choice is kept in the query
  string as `panel-id[filter-name]=value`; a filter with many values repeats the
  param. Defaults (and empty selections) are not written, so an unfiltered page
  has a clean URL. Changing a filter replaces the history entry.
- Routes read and write filters with `useSectionFilterOne` /
  `useSectionFilterMany` from `#/core/infra/component/use-section-filter`, with a
  codec (`stringFilterCodec`, `booleanFilterCodec`, `enumFilterCodec(Enum)`,
  `nullableFilterCodec(...)`) that drops values it doesn't know.
  `FilterFewOptions*` and `FilterManyOptions` are fully controlled: the route
  passes the selected value(s) in.
- `basicShouldRevalidate` and `standardShouldRevalidate` are wrapped in
  `ignoringSectionFilterChanges` (`#/core/infra/section-filters`): a GET
  navigation whose only query difference is in section filters, and which
  changes no route param shared by both URLs, does not reload anything.
  Actions, `useRevalidator()` and `invalidateTopLevel` always get through.
  Routes with their own `shouldRevalidate` wrap it the same way.
- Links carry filters to where the panel owning them is still on screen. Each
  filter hook records the path of the route rendering its panel, and the shared
  link components (`EntityLink`, nav actions in `SectionActions`, the create and
  return links of trunk, branch and leaf panels, `EntityNoNothingCard`) append
  the current filters of every panel whose path the target is at or under. So
  opening an entity from a filtered list, and closing it again, keeps the list
  filtered; going somewhere else drops them.
- The time plan's view and grouping become `time-plan[view]` and
  `time-plan[grouping]`, and `withTimePlanDisplay` carries every `time-plan[...]`
  filter through server-side redirects.

## Consequences

- Filtered pages can be reloaded, bookmarked and shared, and survive panels
  opening and closing over them, without any loader running again.
- Old links using `timePlanView` / `timePlanGrouping` fall back to the default
  view and grouping.
- A new filter needs a panel id and filter name, and must go through the hooks
  rather than `useState`. A new link component that navigates within a page
  should use `useSectionFiltersPreservedTo` / `useSectionFiltersPreserver`.
- Server-side redirects after actions (other than the time plan's) do not know
  about the client's filters and land on the unfiltered page.
- Moving between two sibling panels (e.g. one big plan to another) drops the
  first panel's own filters; if it had any set, the page under it reloads once,
  as React Router cannot tell which route owns a changed param.
