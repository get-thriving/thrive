# ADR 0012: Logging and error handling

## Status

Accepted (2026-08-15)

## Context

Thrive runs fifteen separate processes — WebAPI srv, ten `*-do-all` cron
workers, API, MCP, WebUI, and Published — plus a CLI. Sentry is already the
declared telemetry sink via the `TELEMETRY` blend flag
([ADR 0008](0008.webapi-backend-blend-via-config-global.md)), but the wiring
behind that flag was a stub, and each surface had grown its own ad hoc habits.

A scan of the codebase before this ADR found:

1. **Sentry was initialised with `dsn`, `send_default_pii=True` and
   `enable_logs=True`, and nothing else.** No `environment`, so production,
   staging and per-branch preview deploys all landed in one undifferentiated
   bucket. No `release`, so no regression tracking across versions. No
   `server_name`, so an issue could not be attributed to the process that
   raised it. No scrubbing, while `send_default_pii=True` opted us *in* to
   sending IP addresses and request headers.

2. **Under `TELEMETRY=sentry`, Python logging was never configured at all.**
   `LocalTelemetry.prepare()` calls `logging.basicConfig`; `SentryTelemetry`
   did not. The root logger therefore stayed at its default `WARNING`, so
   every `LOGGER.info` in the codebase — including the "Invoking mutation
   command" audit line in `UseCase.execute` — was dropped. Production had
   strictly *less* logging than a developer laptop, and Sentry's logging
   integration (which hooks `Logger.callHandlers`) never saw those records
   either.

3. **Handled exceptions were invisible to Sentry, regardless of severity.**
   The Starlette integration only auto-captures handled exceptions carrying a
   `status_code` attribute inside `failed_request_status_codes`. Jupiter's
   domain exceptions carry no such attribute, so *nothing* registered in
   `WebApiAppForm` was ever reported — neither the harmless validation errors
   nor a genuine 5xx.

4. **Cron failures were swallowed.** `CronExceptionHandler.handle` logged at
   `ERROR` and returned; `Cron._execute_command` then continued as if the run
   had succeeded. A nightly job could fail every night indefinitely without a
   single alert, and `START_RUN_STOP` runs still exited zero.

5. **No domain context reached Sentry.** The system already threads a
   `trace_id`, a `mutation_id` and a `context_str` through every mutation and
   persists them in `mutation_invocation_record`
   ([ADR 0005](0005.recording-events.md)). None of it was attached to
   telemetry, so a Sentry issue could not be joined back to the invocation
   record that produced it.

6. **API and MCP never actually enabled Sentry in production.** Their Render
   services do not include the `jupiter-webapi-config` / `jupiter-webapi-secrets`
   env groups, so `TELEMETRY` fell back to `Config.global`'s `local` and
   `SENTRY_DSN` stayed at the `FAKEFAKE` placeholder. The `SentryTelemetry`
   branch in their `jupiter.py` was dead code.

7. **WebUI and Published had no telemetry at all**, even though
   `GlobalPropertiesServer` already carries the `telemetry` blend flag and
   ADR 0008 states the flag applies to WebUI. Server-side loader and action
   failures reached `console.error`; browser errors reached nothing.

## Decision

### 1. One seam per language

All telemetry configuration and reporting goes through a single module:

- Python — `jupiter.framework.telemetry`
- TypeScript — `#/core/infra/telemetry`

No other module imports `sentry_sdk` or `@sentry/*`. Swapping or disabling the
vendor stays a one-file change, and `TELEMETRY=local` keeps working as a real,
fully-functional blend rather than a degraded one.

### 2. Every error is either *expected* or *unexpected*

This is the central classification; everything else follows from it.

**Expected** — a legitimate outcome that the caller can act on. Bad input, a
missing entity, an expired token, a denied grant. These are the normal
operation of a correct system. They are logged at `INFO`, recorded as a Sentry
*breadcrumb*, and **never** raise a Sentry issue.

**Unexpected** — a defect or an infrastructure failure. Nobody can act on it
except us. Logged at `ERROR`, and always sent to Sentry as an issue with full
context.

The split is derived, not hand-maintained:

| Surface | Expected | Unexpected |
| ------- | -------- | ---------- |
| WebAPI | a registered `WebApiExceptionHandler` whose `get_status_code()` is `< 500` | anything else, including a registered handler returning `>= 500` |
| Cron | *nothing* — there is no user to act on it | every exception that escapes the use case |
| API / MCP gateway | a 4xx relayed from WebAPI | a timeout, a 5xx from WebAPI, an unparseable response |
| Remix loader/action | `not-found`, `access-denied`, `session-expired` | `error`, `unknown` |
| Browser | a handled hydration mismatch (self-heals via `/app/render-fix`) | any other uncaught error or rejection |

The WebUI's existing `classifyError` in `error-boundary.tsx` already produces
exactly this partition, so it becomes the client-side authority rather than a
parallel notion.

### 3. Logging is always configured, in every blend

`Telemetry.prepare()` configures Python's `logging` in *both* implementations —
Rich-formatted for `local`, plain single-line for `sentry` (Render captures
stdout). Sentry is an *additional* sink, never a replacement for stdout logs.

The severity ladder is fixed:

| Level | Meaning | stdout | Sentry |
| ----- | ------- | ------ | ------ |
| `DEBUG` | detail useful only while developing | development only | no |
| `INFO` | lifecycle: startup, use case invocation, cron run boundaries, expected errors | yes | breadcrumb |
| `WARNING` | degraded but handled: a retry, a fallback, a skipped record | yes | breadcrumb |
| `ERROR` | unexpected: a defect or infra failure a human must look at | yes | **issue** |
| `CRITICAL` | as `ERROR`, plus a data-integrity risk | yes | **issue** |

### 4. Context comes from the domain

Every event carries, as Sentry tags:

- `service` — `webapi-srv`, `api`, `mcp`, `gc-do-all`, `webui`, …
- `universe`, `env`, `instance`, `hosting` — the deployment identity
- `trace_id` — the cross-service identifier already on `DomainContext`
- `mutation_id` — the per-service identifier already on `DomainContext`
- `operation` — the use case class name, cron job name, or route name
- `app_component` — the calling shell/platform/distribution, from the
  `X-Jupiter-FrontDoor` header

The Sentry *user id* is set to the context string
(`user:{ref_id}+workspace:{ref_id}`, or `system` / `guest`) — the exact value
persisted as `mutation_invocation_record.context_str`. An issue in Sentry and a
row in the invocation table can therefore be joined on either `trace_id`,
`mutation_id`, or user.

`environment` is `{universe}-{env}` and `release` is `thrive@{version}`, so
production, staging and preview deploys separate cleanly and regressions are
attributable to a version.

### 5. Identity is ids only; payloads are never sent

`send_default_pii=False`. The only identity attached is the user and workspace
`ref_id` (via the context string). No email address, no name, no IP address, no
request body.

Use case **arguments are never sent** — they carry journal entries, notes, and
doc contents. Only the args *type name* is attached. This is a deliberate
divergence from `mutation_invocation_record`, which does persist args, because
that table is inside our own database and Sentry is not.

A `before_send` hook additionally scrubs any key whose name looks secret —
`token`, `secret`, `password`, `api_key`, `dsn`, `cookie`, `authorization`,
`credential`, `private_key` — recursively across event extras, contexts,
request data, breadcrumbs and log attributes, replacing the value with
`[scrubbed]`. The hook is defence in depth: nothing should reach it, and it
catches the cases where something does.

### 6. Sampling

- `traces_sample_rate` = `0.1` for request-serving processes (WebAPI, API, MCP,
  WebUI, Published) — enough for latency and distributed traces without
  meaningful quota spend.
- `traces_sample_rate` = `1.0` for cron workers — they run at most hourly, so
  full tracing is nearly free and a slow nightly job is exactly the thing worth
  seeing.
- Health check routes (`/healthz`) are dropped from tracing entirely; Render
  polls them constantly and they carry no signal.
- Error events are never sampled.

### 7. Where each surface reports

| Surface | Mechanism |
| ------- | --------- |
| WebAPI handled exceptions | `WebApiExceptionHandler.attach_handler` routes through the expected/unexpected split |
| WebAPI unhandled exceptions | Sentry's ASGI integration captures on re-raise; a catch-all handler only *shapes* the 500 into the standard `ErrorResponse` body, and deliberately does not report, to avoid a duplicate event |
| WebAPI request scope | middleware binds deployment tags, `trace_id` and `app_component` before the route runs |
| Use case invocation | `UseCase.execute` binds `operation`, `mutation_id` and the actor, and logs the invocation at `INFO` |
| Cron | `Cron._execute_command` reports every escaping exception, keeps the scheduler alive in `RUN_FOREVER`, and re-raises in `START_RUN_STOP` so the process exits non-zero |
| API / MCP gateway | timeouts and upstream 5xx are reported at the point they are turned into a 502/504 |
| Remix server | Remix's `handleError` export, filtered through the same classification |
| Browser | `@sentry/remix` client init, plus explicit capture from the route error boundaries |

### 8. The CLI stays out

The CLI runs on a developer's or user's own machine against their own data.
It configures logging but never initialises Sentry — shipping a laptop's
stack traces to our project is neither useful nor ours to collect. Its existing
`CliExceptionHandler` console rendering is unchanged.

## Consequences

- `Telemetry` gains a real interface (`prepare`, `bind_actor`, `bind_operation`,
  `record_expected_error`, `record_unexpected_error`, `scope`) implemented by
  `LocalTelemetry`, `SentryTelemetry` and `NoOpTelemetry`. Adding a surface
  means implementing against that interface, not calling a vendor SDK.

- Appforms and framework services take a `Telemetry` and pass it to their
  exception handlers, so reporting is explicit and testable. The one exception
  is `UseCase.execute`, which reaches a process-wide *current telemetry*
  accessor rather than adding a constructor parameter to every use case in the
  codebase; the accessor is set by `prepare()` and defaults to `NoOpTelemetry`.

- API and MCP now consume the shared WebAPI env groups on Render so that
  `TELEMETRY` and `SENTRY_DSN` actually reach them.

- WebUI and Published take a browser DSN (`SENTRY_PUBLIC_DSN`) distinct from the
  backend DSN, because a browser DSN is public by construction and should point
  at its own Sentry project.

- Anyone adding a new exception type only chooses a status code; the
  expected/unexpected split — and therefore whether it pages someone — follows
  automatically. Getting alerting wrong now requires getting the HTTP semantics
  wrong first.
