# Multiple auth methods per user

## Context

A user used to have exactly one way to sign in: `User.auth_method` was `local`,
`google` or `apple`, and every login path refused a user whose method was
another one. The data model already allowed more (`User` holds an optional
`AuthLocal`, `AuthGoogle` and `AuthApple`), but nothing could add a second one.
Someone who signed up with a password and later pressed "Sign in with Google"
with the same email hit the unique email constraint and got a dead end.

## Decision

- **The auth records are the source of truth.** A user can sign in with a method
  if the matching `AuthLocal`, `AuthGoogle` or `AuthApple` row exists. The login
  paths no longer look at the user's method. `load_linked_auth_methods` lists
  them and `LoadTopLevelInfo` returns them as `user_linked_auth_methods`.
- **`User.auth_method` is now `auth_sign_up_method`.** It records how the
  account was created and never changes. It drives the tag in the UI and which
  provider is allowed to rewrite the profile.
- **Linking needs a signed in session.** The Account page links Google or Apple
  through the same OAuth redirect (`LinkGoogle`, `LinkApple`, and their native
  variants), and adds a password with `AddLocalAuth` (verified email only, and
  it issues a recovery token). A provider account that already belongs to
  another user is refused, as is a second account of the same provider.
- **No link at the collision point.** A sign in that would create a user whose
  email is taken fails with `AccountExistsWithOtherAuthMethodError`, naming the
  methods that account has and saying the new one can be linked from the Account page.
  Auto-linking by email is how accounts get taken over, and Apple's private relay
  emails would not match anyway.
- **Unlinking** (`UnlinkAuthMethod`) is allowed while another method remains.
  Unlinking Apple revokes its refresh token, as closing the account does.
- **Provider upkeep runs for every linked row.** The daily Google and Apple jobs
  walk the auth records instead of the users of that sign up method, so a
  secondary link still gets its refresh token renewed or marked expired. Only
  the sign up method may update the profile: the email is the local login key,
  so a linked provider must never rewrite it.
- **Closing an account** revokes Apple if it is linked, whatever the sign up
  method was.

## Consequences

- No migration beyond the column rename.
- In the mobile shell the Account page links through the Google and Apple
  SDKs (`lifecycle/link/{google,apple}/native`), as sign in does. Android has no
  native Apple, so Apple can't be linked there.
- Unlinking Google does not revoke its token at Google; it only drops ours.
- Which email wins on conflicting provider profiles was settled by not letting
  secondary providers write at all.
