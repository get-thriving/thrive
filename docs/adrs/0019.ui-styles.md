# ADR 0019: UI styles

## Status

Accepted (2026-11-07)

## Context

The WebUI is getting a second look, Strata: dark, dense, one accent, IBM Plex
type, rows instead of cards, side-by-side columns and an icon rail. The two
looks differ in colour and type, and over time also in layout and interaction
flows (columns instead of overlays, a keyboard model, editors with an unsaved
changes bar).

Keeping two UIs for good would double the cost of every later UI change. The
only user is the owner, so there is no one to protect with a long transition.
Strata is therefore built **on a long-lived feature branch** next to the
current look (called classic), behind a per-user preference, and released
**once**, as the only UI.

## Decision

### While Strata is built (on the feature branch)

- **A per-user preference, `ui_style`.** A `UiStyle` enum (`classic` |
  `strata`) on `WebUiSettings`, next to `use_night_mode`, defaulting to
  `classic`. It is changed with the existing web UI settings update use case,
  from the Appearance card on the account page. It is a development tool: it
  lets us flip between the two to compare and to catch regressions.
- **A cookie for SSR**, `_jupiter_ui_style`, written and cleared the same way
  as the night mode cookie: host-only, and readable by the pre-hydration
  script. The root loader reads the setting when logged in and falls back to
  the cookie.
- **One theme per style.** `buildTheme(useNightMode)` stays the classic theme.
  `buildStrataTheme()` (`infra/component/strata-theme.ts`) is built from
  `strata-tokens.ts`. The root route picks one. Restyling goes through theme
  overrides first, then small styled wrappers, and only then conditional
  layout.
- **Strata is dark-only.** Turning it on forces night mode, including the
  pre-hydration paint, and the Night Mode switch is disabled while it is on.
  The saved night mode preference is kept, so it comes back when Strata goes
  off. A light variant needs a design first.
- **Layout variants are gated on the preference**, never on forked route files.
  Loaders and actions are shared. Behaviour (selection, keyboard handling,
  unsaved-changes state) lives in hooks both styles use; only markup and layout
  containers branch, and each branch stays thin. A component that lays out
  differently reads the style from the root loader data and branches in the
  shared layout components.
- **Every action stays reachable.** Classic is the contract for what a screen
  can do. Strata may change how it is done, not whether.
- **Classic is frozen.** It gets fixes needed to keep it working, and nothing
  else, until it is deleted. It no longer has to stay pixel-identical, and
  intermediate pull requests into the branch may leave things rough as long as
  the branch is green at the end.
- **The rail has two widths.** The Strata rail is the 52px icon rail, or
  176px with labels when the user turns on `use_expanded_rail`, a second
  `WebUiSettings` field next to `use_night_mode`. Unlike `ui_style` it is a
  permanent setting and survives the release. It can be changed from the
  account page, and from the toggle on the rail itself, which saves it with a
  fetcher and keeps its own local state so the rail answers at once. The
  labelled width is only offered from the `lg` breakpoint up, so it leaves the
  columns their room.
- **Panels become columns.** With Strata on and a big screen, the trunk,
  branch, leaf and leaflet panels (and tool pages, where a trunk would be) are
  fixed to the window side by side, right of the rail. How wide each is, and
  which fold, is the unit layout of [ADR 0020](0020.strata-unit-layout.md).
  The panels stay where they are in the route tree, so no route file changes
  for it: each asks a `StrataColumnsProvider` (in the workspace route) for its
  place. The panels' own markup was made for a full-width page, so a frame
  squeezes it with a few selector overrides instead of every panel growing a
  variant. Outside the provider, and on small screens, the panels render as
  they always did.
- **Fonts are self-hosted** (`@fontsource/ibm-plex-*`), like Inter and
  Fraunces, so self-hosted instances work offline.
- **Components do not contain hex values.** They use the theme, or the tokens
  module.

### Release (one merge to `develop`)

Nothing else lands on `develop` while the branch lives, so it is not synced
along the way. Before the single merge:

1. Every screen in the brief is done in Strata, and the browser tests pass.
2. **Classic is deleted**: its theme, its layout branches, and the `ui_style`
   setting, the `UiStyle` enum, the `_jupiter_ui_style` cookie, the account
   page switch and the Night Mode lock. Strata becomes the only UI.
3. **The `ui_style` migration is deleted with the setting.** It was never
   released, so nothing has to be undone. The migration chain is checked again
   so both SQLite and Postgres stay linear.
4. Client code is regenerated, `mise run check` and the full itests pass, and
   this ADR is updated to describe the final state: one UI, one theme.
5. The merge is kept revertable as a unit.

### Open questions for the release

- **Published pages** use the classic theme today and are not covered by the
  preference. They need a decision before classic is deleted: restyle them with
  Strata, or keep a small standalone theme for them.
- **Night mode.** With Strata dark-only and the only UI, the Night Mode setting
  has no effect and goes with classic, unless a light variant is designed.

## Consequences

- Until the release, both UIs exist: a second palette, typography and component
  override set must be kept in step when shared components change.
- The IBM Plex CSS is loaded for everyone while both exist, as small
  `unicode-range` split files the browser only fetches when used.
- Published pages stay classic until the decision above is made.
- Because the preference never reaches production, the final change has no data
  migration for it, and no escape hatch back to classic.
- The release is one large diff with nothing proven in production beforehand.
  Reviewing it, and its revertability, are what keep that safe.
