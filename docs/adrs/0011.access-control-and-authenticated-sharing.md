# ADR 0011: Access control and authenticated sharing

## Status

Accepted (2026-08-08)

## Context

Thrive needs authenticated users to share crown entities with each other —
todos, vacations, docs, calendars, and similar — without exposing the whole
workspace. Public unlisted sharing for guests is already covered by
[ADR 0010](0010.entity-publish-mechanism.md) (`PublishEntity`). That mechanism
must stay separate: publish is capability-link + guest read-only; access
control is identity-based grants between logged-in users.

Product requirements that shaped the design:

- Sharing is **opt-in per entity type** (explicit allowlist).
- Effective rights must be cheap to check on every load/find/mutation.
- Parent shares must cascade to children (metric → entries, smart list → items,
  schedule stream → events, docs folder → nested docs/dirs), while a stronger
  direct grant on a child still wins.
- Owners invite others; non-owners can request access; invitees get an
  acknowledge / decline flow; collaboration has a dedicated inbox surface.
- Find/list UIs show entities **across workspaces** the caller can access, with
  owner identity visible.
- Forget (grantee leaves) and remove-grant (owner revokes) are distinct
  operations; forget redirects away from the leaf so the UI does not reload a
  now-denied entity.

## Decision

### Domain root: `AccessDomain`

All access structures live under a singleton root
`AccessDomain` (`src/core/jupiter/core/common/sub/access/`), analogous to the
CRM singleton. It is never created from application code; repositories load it
via `load_the_access_domain()`.

Children / records:

| Concept | Kind | Role |
| ------- | ---- | ---- |
| `AccessGrant` | leaf support entity | Source of truth for a principal’s rights on an entity |
| `AccessStatus` | **record** (derived) | Materialized ACL row used for enforcement and indexing |
| `AccessRequest` | leaf support entity | Ask from a user for a level on an entity (owner decides) |
| `AccessInvite` | leaf support entity | Unacknowledged pointer at a newly created grant |

### Access levels

`AccessLevel` is ordered: `reader` < `commenter` < `writer` < `owner`.

- `allows(required)` implements the ranking check used everywhere.
- Only `reader` / `commenter` / `writer` are **invitable** (`is_invitable`);
  ownership is never assigned through invite or request flows.
- Creating a crown entity grants the creator `OWNER`.

`PrincipalType` currently only supports `USER`. Grants and requests reject other
principal types.

### Grant vs status (source of truth vs materialization)

**`AccessGrant`** is what the product mutates: invite, update level, remove,
forget. Fields: `entity` (`EntityLink` with purpose `std`), `principal`,
`user_ref_id`, `access_level`.

**`AccessStatus`** is a fully derived ACL record keyed by
`(access_domain, entity, user_ref_id)`. It stores effective `access_level`,
`reason` (`GRANT` or `INHERITED`), and `access_grant_ref_id` pointing at the
grant that produced the row.

Enforcement never recomputes hierarchy on the hot path: load/find/mutation
bases consult `AccessStatus` via `CheckForAclService` / `LoadForAclService`.
Missing status and insufficient level raise
`UserNotAllowedAccessToEntityError`; missing entities are reported as
`EntityNotFoundError` so denials do not leak existence incorrectly when the
entity truly is absent.

Search indexing follows the same split: ordinary entity mutations reindex with
current readers; `AccessGrant` mutation events update visibility for affected
entities (via status / grant-derived helpers next to `AccessStatus`).

### Allowlist and cascade-only types

Shareable `EntityLink.the_type` values are enumerated in
`ALLOWED_SHARED_ACCESS_OWNER_TYPES` in
`src/core/jupiter/core/common/sub/access/shareable.py`. Unknown types
reject invite/request/remove.

Some types are allowlisted for **cascade / inheritance only** and are not
collaboration entry points (no invite UI, omitted from collaboration lists):

- `TIME_PLAN_ACTIVITY` — cascade from time plan
- `SMART_LIST_ITEM` — cascade from smart list
- `METRIC_ENTRY` — cascade from metric

Direct sharing is for crown entities that are meaningful share roots; leaf
support entities are out of ACL scope unless explicitly allowlisted as above.

### How rights propagate

1. **`GrantRightsToUserService`**  
   Upserts a grant + `GRANT` status on the target, then walks
   `ContainsLink` / `OwnsLink` children and upserts `INHERITED` statuses (same
   level, same `access_grant_ref_id`). Re-grants are idempotent upserts.

2. **`ReplicateParentRightsForEntityService`**  
   On create of a shareable child, walk ancestors that are themselves
   shareable; inherit each ancestor’s grants onto the child. Closest ancestor
   wins per user (one effective status per user). When the framework
   `ParentLink` is not the share root (e.g. schedule events parent to
   `ScheduleDomain` but are owned by a stream via `OwnsMany`), also inherit
   from shareable OwnsLink/ContainsLink parents discovered by
   `FindShareableOwnsParentsService` — the same materialized `INHERITED`
   statuses metrics/smart lists get via their ParentLink walk.

3. **Docs directory hierarchy**  
   Docs/dirs use an explicit parent-dir chain (`parent_dir_ref_id`), not only
   framework owns/contains links.
   `ReplicateDirHierarchyRightsService` reconciles: for each user, effective
   access is the **strongest** of a direct `GRANT` on the entity and
   `INHERITED` access from any ancestor directory grant. Sharing a folder
   therefore gives every nested doc/subdir at least that access; a stronger
   child grant still wins. Domain-specific refresh after grant changes is
   registered in `REFRESH_ACCESS_FOR_ENTITY_SERVICES`
   (`shareable.py`): `RefreshDocAccessService` /
   `RefreshDirAccessService` implement `RefreshAccessForEntityService` and
   are invoked via `refresh_domain_specific_access_for_entity`.

### Crown use-case bases (enforcement API)

ACL is pushed into shared bases in `crown_entity_support.py` rather than
ad-hoc workspace-id checks:

| Base | Typical required level | Notable helpers |
| ---- | ---------------------- | --------------- |
| `JupiterLoadCrownEntityUseCase` / find | `READER` | `load_entity`, `check_entity`, `find_all_entities` |
| `JupiterCreateCrownEntityUseCase` | create + `OWNER` grant | `create_entity`, `grant_access_after_create`, `check_can_share` |
| `JupiterUpdate` / archive / remove | `WRITER` | `load_entity` / `check_entity` at writer |

`AclCrownEntityWriter.create_entity` always:

1. Persists the entity.
2. Replicates parent rights onto it.
3. Grants the creating user the requested level (default `OWNER`).

Cross-workspace listing for shared entities must **not** constrain
`parent_ref_id` to the caller’s collection. Find paths use
`find_all_entities` / ACL-filtered generic finds so shared items from other
workspaces appear. Background/gen paths take an `AclCrownEntityReader` /
writer rather than unrestricted access flags.

Shared **writers** may update/archive/remove when status allows. OWNER-only
operations (invite/share administration, some tag/contact/publish controls)
stay owner-gated; UI disables them via `accessStatus`.

### Collaboration lifecycle

```text
Owner invites user ──► AccessGrant + AccessInvite + statuses (+ cascade)
                         │
Invitee acknowledges ──► archive AccessInvite (grant remains)
Invitee cancels/forgets ► archive invite + remove grant (forget)

Non-owner requests ──► AccessRequest(status=requested)
Owner accepts ───────► request accepted + same grant path as invite
Owner rejects ───────► request rejected
Requester cancels ───► archive outgoing request
```

Use cases live under `common/sub/access/use_case/` (invite, request, accept,
reject, cancel request, acknowledge invite, cancel invite, remove grant,
forget/remove access, get access for entity, find collaborations, search for
user, load grant/invite/request).

`FindCollaborationsUseCase` returns, newest first:

- unacknowledged invites
- shared with me / shared by me (non-owner grants on collaboration entity types)
- incoming / outgoing requested access requests
- subject `UserLight`s for display

Home summaries expose invite + incoming-request counts for toolbar badges;
a collaboration home widget surfaces ack/deny actions.

### Workspace UI conventions

- **Leaf**: `LeafPanel` with `accessable`, `accessOwner`, `accessStatus`;
  `AccessPanel` for grant management; inputs gated with
  `accessStatusAllowsWriterOrAbove`.
- **Trunk**: owner chip (`UserLightChip`) on cards so foreign-owned shared
  entities are obvious.
- **Forget**: remove-grant / forget actions redirect to `returnLocation` (trunk);
  do not stay on the leaf (loader would 401) and do not skip revalidation of
  the trunk list.
- **Collaboration**: Core → Collaboration trunk with tabs for invites,
  requests (to-me / from-me), and grants (to-me / from-me), plus detail leaves
  under `core/collaboration/...`.
- **Docs special UI**: shared roots surface under the viewer’s own docs root;
  navigating a shared subtree can return to own root; parent “..” hides when
  the parent dir is not accessible.
- **Inherited grants in AccessPanel**: when effective status comes from another
  entity, UI highlights that and links the source; forget is only offered on
  the grant-owning entity, not inherited rows.

Public publish remains independent: guest loaders use `PublishEntity` and must
not rely on `AccessStatus`. Authenticated load may return `access_status=None`
for guest/public paths.

### Adding sharing to an entity type

Canonical checklist lives in `.cursor/skills/add-entity-sharing/SKILL.md`
(vacations/todos as references). Minimum:

1. Allowlist (+ cascade rules if parent/child).
2. Create path grants `OWNER` via crown create.
3. Load/find return `owner` + `access_status`; find is cross-workspace.
4. Mutations use crown ACL bases; only ACL-check retargeted foreign refs when
   they change.
5. Leaf `AccessPanel` + trunk owner chip; generate clients; API + WebUI ACL
   tests (no grant / reader / writer).

## Consequences

- Every shareable crown create must grant ACL (and replicate parents); missing
  grants look like “entity exists but nobody can load it,” including home
  widgets and other non-obvious crown types.
- AccessStatus must stay consistent with grants and hierarchy. Grant mutations
  cascade statuses; docs/dir moves and hierarchy refresh go through
  `ReplicateDirHierarchyRightsService`. Do not treat status as independently
  editable product state.
- Cascade-only allowlist entries must not become collaboration invite targets.
- Publish (ADR 0010) and access grants answer different threats; wiring
  `accessable` / owner chips does not imply a public publish panel, and vice
  versa.
- Find/list bugs that filter by the caller’s collection parent silently hide
  shared entities — prefer `find_all_entities` / ACL-aware readers.
- Search and any “visible to users” index must update on grant changes, not
  only on entity field mutations.
- Extending principals beyond `USER` requires schema, validation, and UI work;
  commenter level exists in the enum but product surfaces today emphasize
  reader/writer.
- Integration tests for ACL (API + WebUI) are part of the sharing contract for
  each allowlisted type.
